# SkillHub 上游合并

先读[工程入口](../../../.trellis/spec/index.md)、[工作流](../../../.trellis/spec/workflow/index.md)和[测试入口](../../../.trellis/spec/testing/index.md)，按受影响领域读取正文。工程和业务规则引用仓库契约，不将参考项目的 Go 主程序、登录策略或功能排除规则搬入 SkillHub。

## 来源与接续

检查仓库、分支、Git 状态、`MERGE_HEAD`、实际远端及会话授权。优先复用已有任务记录；没有记录时，按项目多步任务约定建立本地记录，保存固定提交、决策、进度和验证，记录不进入业务提交或二开日志。

当前仓库不保证有 `upstream` remote。用户指定来源优先；否则从已核实的远端与项目来源识别，不能把 GitLab origin 当上游，也不向上游推送。缺少可靠 URL/ref 时仅询问缺失项，先完成独立的本地调查；不凭 README 中的项目链接添加远端。

新合并前保护无关修改。需要隔离时使用独立 worktree，分支默认 `codex/upstream-YYYY-MM-DD`，避免覆盖已有同名分支。不得擅自 stash、reset 或清理。已有本次合并时核对记录与 Git 状态，续接未完成步骤，不重新 fetch、换基线或重复 merge。

## 调查和执行

1. 获取已确认来源，固定 `local-before`、`upstream-tip`、共同基线及目标分支；之后用 SHA 比较。读取 `changes/CHANGELOG.md` 及相关详情；尚无日志时使用本地历史和实际实现识别定制，不能视为没有二开。
2. 比较基线到上游、基线到本地，交叉识别双方修改的文件。给出按功能的影响摘要后，在隔离分支执行 `git merge --no-commit --no-ff <固定upstream-tip>`。冲突退出码在存在 `MERGE_HEAD` 时进入解决流程；其他错误按实际原因处理。
3. 冲突文件及双方改过的自动合并文件，先查完整双方版本、调用方、类型、配置、依赖和本地功能，再记录“本地逻辑、上游逻辑、保留本地／采用上游／手工合并的具体结果、唯一推荐及理由”。双方兼容时手工整合，随后直接执行和精确暂存；不将普通兼容选择交回用户逐文件确认。
4. 禁止批量 `-X ours/theirs` 或批量选边。单文件采用某侧前检查整份内容，避免丢掉非冲突区域。无法兼容的业务语义先依据契约调查；确实需要改变未授权的权限流程、公共契约或破坏性迁移时，提出具体决策，并继续无依赖工作。
5. 审查自动合并、新增、删除及重命名。跟踪依赖和生成物，核对注册表行为、SKILL.md 包兼容、namespace/CLI 契约、身份类型、存储与搜索接口及操作审计。关注 Flyway 版本和 checksum 冲突，不通过删除迁移或 repair 掩盖。
6. `.agents/`、`changes/` 及 `.trellis/spec/` 若双方存在内容，逐项比较；保护本地工具和记录，不把目录名当作永久选边策略。上游同步和仅维持原行为的冲突适配不写二开日志。

## 验证和完成

冲突列表为空仍需审查最终差异。按固定上游 SHA 核对未接入的逻辑，解释保留差异，检查跨模块调用、API 生成类型、依赖锁文件和迁移。按测试矩阵运行适用检查；后端 app 使用 `make test-backend-app` 或带 `-am` 的等价命令。生成 OpenAPI 检查及 staging 可能启停服务，先读实际脚本和隔离范围。

用户只授权合并时交付已解决、已审查、已验证的待提交结果；不因缺少提交授权提前跳过这些工作。已有提交或推送授权时按 [git-commit-push](../git-commit-push/SKILL.md)继续；已完成 merge commit 后按 [upstream-merge-review](../upstream-merge-review/SKILL.md)交接。未提交时明确为阶段结果，不冒充已完成合并。

报告关键行为与 UI 变化、本地功能保留、未接入内容、决策及证据、验证通过／失败／未运行／受阻、上线前提和下一步。分支、worktree 和记录默认保留供续接；清理须有授权并按[任务归档](../../../.trellis/spec/workflow/task-archive.md)核实，禁止强删或清除其他任务。
