# SkillHub main 上游合并与部署

本技能面向用户明确要求的一次 main 全流程：合并、验证、提交推送、镜像发布、SSH 更新及核验。创建、编辑或解释技能不执行流程。未指定目标时不沿用当前 v1 或参考项目服务器；不创建 PR，也不顺带发布 CLI/npm、Helm 或公告。

先读[工程入口](../../../../.trellis/spec/index.md)、[部署规范](../../../../.trellis/spec/deployment/index.md)、[测试入口](../../../../.trellis/spec/testing/index.md)、[部署手册](../../../../docs/09-deployment.md)、[镜像发布](../../docker-publish/SKILL.md)和 [SSH 目标契约](ssh-target.md)。

## 输入与隔离

读取未跟踪且被忽略的根目录 `.main-upstream-deploy.local.json`，按参考核实 git、publish、ssh 目标。主机及路径只从该配置或用户已明确的输入取得。缺项集中说明；不读取其他项目配置或添加当前工作区 remote。

在独立临时目录克隆 fork 的 main，只在此进行 Git 写入。记录当前工作区位置但不切分支、不暂存用户改动、不改当前 v1。固定 fork main SHA、上游 SHA 及共同基线，将进度保存到本地任务记录，不放入业务提交或二开日志。

## 合并与发布

1. 获取指定上游分支，预览变更及本地差异，按领域契约识别兼容性、审计和迁移影响。出现需要改变未授权业务规则的决策时停止相关步骤并说明，不能静默删本地能力。
2. 在临时克隆的 main 合并固定 SHA，使用 `--no-ff --no-commit` 留验证窗口。无冲突时审查自动合并；有冲突则在本次干净隔离克隆执行 `git merge --abort`，报告需转入 [upstream-merge](../../upstream-merge/SKILL.md) 的冲突，不能自动批量选边。
3. 按影响矩阵完成验证，后端 app 检查含依赖模块。必要环境不可用或检查失败时停止发布，保留隔离克隆与证据。验证通过后以现有用户身份创建带 sign-off 的英文 merge commit；无合并变化时不造空提交。目标已包含上游时，仍核实将发布版本及现有验证证据。
4. 使用普通 `git push origin HEAD:refs/heads/main`。并发 non-fast-forward 时只允许重新获取 main、重新比较/合并/验证后再重试一次；有冲突或仍失败就停止，不强推。提交信息拒绝仅按 [git-push-skip-lint](../../git-push-skip-lint/SKILL.md) 的条件回退。
5. 核验 fork 远端 main tip。发布 GitHub 仓库 main 必须指向相同 SHA；若使用镜像同步，最多等待 5 分钟，每次间隔不超过 30 秒，未一致则停止，不构建旧版本或自动向另一个仓库推送。
6. 按 Docker 技能发布该 main，确认运行 headSha 等于已推送 SHA，并核实四组件产物。任何构建失败、源版本变化或产物缺失均阻止 SSH 更新。
7. 按 SSH 参考选择性更新已配置的实例及应用镜像，拉取并重建，核验运行版本、健康与公开入口。该路径使用 SSH，不调用 1Panel，也不混用面板配置。

每个阶段成功且证据明确才进入下一阶段。超时/结果不明先只读查询，不能重新推送、重新触发 workflow 或重建；自动重试仅限上述明确分支。

## 交付

报告 main 最终 SHA、Git 推送及验证、工作流 ID/链接、组件镜像/digest、SSH 目标及目录、实际命令结果、服务健康和版本证据；说明临时克隆/进度记录位置及限制。命令成功不等于业务验收完成。任一阶段失败时写出已完成、失败和未执行阶段，保留当前服务与数据，不自动回滚、删除分支或清理工作区。
