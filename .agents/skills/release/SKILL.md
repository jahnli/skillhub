# SkillHub 应用发布

创建或解释技能不执行发布。用户明确调用本流程即授权一次镜像发布及其成功后对选定 1Panel 目标的更新、拉取和应用服务重建；不自动提交、推送、创建标签、发布公告或发布 npm 包。

先完整读取 [docker-publish](../docker-publish/SKILL.md)、[1panel-deploy](../1panel-deploy/SKILL.md)及其按需参考，并按各自契约执行。本技能只串联阶段。

## 发布输入

确定 GitHub 仓库、workflow/ref、1Panel 目标及组件范围。当前项目只有已核实的 GitLab origin，不能据此猜 GitHub 仓库。读取本地目标的非敏感字段以核实配置完整性，密钥仅在需要请求时使用；缺少配置时在触发发布前集中询问缺项。用户已明确的目标无需再次选择。

默认 Docker Hub 四组件路径。明确要求 GHCR 时遵循其不同标签和架构规则。本技能不创建或推送 `v*`、`cli-v*`、`dsh-v*` tag；项目 `release-notes.yml`、`release-cli.yml` 和其他工作流有独立副作用。用户要求正式版本、CLI/npm 或 Helm 发布时先核对相应工作流与授权范围，不将应用部署流程代替它们。

## 阶段和停止条件

1. 确定远端 source SHA，按 Docker 技能触发一次并跟踪唯一运行。发布失败或状态不明时停止，1Panel 未执行；部分矩阵已推送的镜像如实报告。
2. 仅工作流成功且待部署组件的完整镜像、版本/digest 与同一 source SHA 全部核实后继续。把组件映射传给部署阶段，不从 `latest` 或本地 git describe 生成部署版本。
3. 目标镜像仓库与实际产物不符或版本来源不明时报告“镜像发布完成，部署阻塞”，不替换成上游官方镜像。
4. 按部署技能核实编排与迁移条件，再执行一次更新并等待。多个环境复用同组产物，依次更新、各自验收；失败后停止后续环境，不自动重跑或回滚。
5. 服务、镜像、健康及受影响业务的证据分别汇总。容器启动成功但版本无法核实或健康异常时不能宣称发布全部成功。

调用 `/release` 时默认包含本流程的发布和部署；用户明确仅构建或仅部署时按该范围使用对应技能，不扩大操作。

## 交付

简洁报告整体成功／部分完成／失败／受阻、GitHub 仓库/ref/SHA、运行 ID 和链接、各组件版本镜像/digest，以及逐环境 taskID、容器状态、健康结果与访问地址。缺少字段写未核实，未执行阶段写明原因。说明迁移及未验证的业务范围；所有轮询单次不超过 30 秒，每 60 秒内更新进度。
